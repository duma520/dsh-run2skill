> 1.4.0 修界面上的三个真问题：①面板内容超出后没有滚动条、底部根本看不到；②「自动跳过」的经验也逐条列成待办卡片、却只给一个按钮，等于假选择——现在折叠成一条汇总行 + 一次批量「知道了」；③「高级召回」原来只有一句术语，看不懂该不该勾——现在写清了它做什么、要不要开、开了要自备什么。

> 1.4.2 把开发依赖的已知漏洞从 23 条清到 0 条（`undici` / `vite` / `fast-uri` / `ansi-regex` / `source-map-js` / `katex` 等），插件运行代码一行未改，功能与 1.4.1 完全一致。
> 1.4.3 修两个真实缺陷：① **从左侧栏点开的「技能沉淀」面板六个区全空。** 根因是侧栏面板走的是直接渲染路径，不走宿主的 `inject`，拿不到会话/工作区订阅，于是作用域退化成「仅用户」层级、被后端按作用域不一致拒绝；现在面板自己订一份，并记住最后一个真实选中的会话，切到面板时不会一下子变空。② 「作用域不可用」健康码一直刷、却不知道为什么：原来那个 `catch` 是空的，真实错误被吞掉；现在把原因写进日志（`plugin.scope_unavailable`）。
> 1.5.0 修的是「**为什么它从来学不会任何 Skill**」这个根本问题，并给了一个能一次清场的按钮。三个真缺陷：① **模型回复里带 `reasoning` / `tool-call` 块时，整条观察被判成不完整** —— 而模型的正常回复形态就是这种混排，实测 265 个历史轮次里 **245 个**死在这一条；不完整的观察按规定必须清空证据，于是检测器拿不到任何证据、把所有模型答案都判成「没绑定证据」，表现就是永远停在「语义检测」这一步。② **路由继承的回填分支永远不触发** —— 一个标志位在新会话首次扫描时就被置为「已绑定」，而那时路由还是空的，于是「往前回读日志补路由」这段永远不跑；20 轮的会话里有 11 轮窗口内根本没有 `request/header` 事件，全靠继承，继承一断就整批判 `ROUTE_UNAVAILABLE`（历史 419 条）。③ **带图片的轮次不再被整条丢掉** —— 同一轮里只要有一个文字块，就只用文字部分做证据（纯图片轮次仍然失败关闭，不猜）。另外「需要处理」区新增 **一键全部不再处理**：一次清掉所有只有「不再处理」一个选项的条目，带「重试」的条目不会被它动到，仍然留在下面单独等你决定；任何条数都显示这个按钮，点之前有二次确认、写明不删任何数据。
> 1.6.0 把「没路由就只能等死」这条路堵上了：设置页新增 **语义检测用哪个模型** 一区，可以指定检测时用哪个 provider / model，再选一个兜底模型。原因是 `request/header` 是唯一能证明"这一轮到底用了哪个模型"的事件，而 DSH 并不是每一轮都记它——那种轮次没有任何可观测的路由，以前直接判死、再也不重试。现在这类轮次会用你在这里指定的模型照常整理；某一轮本身带着可用模型信息时，仍然优先用那一轮的，不会被覆盖。模型清单从这台设备上已接通的 provider 现读，选 provider 会自动清空 model（避免留下跨 provider 的无效组合）；宿主不提供清单时退回手填文本框。用兜底模型跑出来的批次会带上 `fallback` 标记，方便以后核对这一条不是用会话原本模型整理的。两项都不填也可以，此时行为与 1.5.0 完全一致。
> 1.6.1 修一句会误导人的话。以前「新建会话还没选工作区」「会话目录不在任何已登记项目里」这类**完全正常**的情形，后端回的是同一个 `conflict`，界面上被统一说成「读不到整理状态、多半是归属对不上」，看着像插件坏了。现在这种情况单列为 `UNSCOPED`，界面直接说「这个会话不在当前项目里（可能是刚新建还没选工作区，或它的目录不在项目范围内）」。真正读不到的 ERROR 文案也改了，不再把「归属对不上」当成默认解释；反过来，如果会话确实绑定了某个项目、却被按「仅用户」层级去问，仍然照样拒绝——那一侧才是真的越界，不能被这次放宽带过去。
> 1.6.2 修两个「明明做了功能却用不上」的接线错误。①设置页的模型清单一直读不到——`model-catalog/list` 与「技能使用情况」用的 `recall-telemetry/list` 这两个端点，当初写好了 RPC，却忘了登记进客户端的端点白名单，调用一进去就抛「unknown endpoint」，界面于是永远退回「手动填 provider / model 的 id」的文本框。②面板没有滚动条——侧栏容器没有定高，`height:100%` 退化成 `auto`，既撑不满也不滚；当时补了 `max-height` 与显式滚动条样式，但方向是错的（详见 1.7.0）。另外「模型」一栏在能读到清单时一律是下拉框：只有选中一个「列不出任何模型」的 provider 时才退回文本框。
> 1.7.0 把「语义检测用哪个模型」从**两段固定字段**改成**用户自己排的优先次序**，并把面板滚动真正修好。①以前只能填「主选」和「兜底」两个位置，而且必须先选 provider 才能选 model；现在是一张有序候选列表，最多 8 行，每行一个 provider+model 组合，可用「上移 / 下移 / 删除」自由排序，检测时从上往下逐个试、第一个能用的就赢。存在插件自己的存储域里，不再走宿主那套「写失败只回一个 false」的配置表单通路——所以**选了存不住**这个毛病从根上消失，写失败也会把宿主原话显示出来（`未保存：<原因>`），不再静默弹回「不指定」。②滚动：此前 `.page` 上写着 `height:100%` + `max-height:calc(100vh - 88px)` + `overflow-y:auto`，其中那个硬编码视口高度是真正的祸首——它与实际可用高度无关，侧栏里让页面长到超出父容器被抓去裁掉、详情页里又把宿主的滚动容器顶掉。1.4.0 与 1.6.2 两次「修滚动」都在往这一层加声明，方向反了。v1.7.0 先把这套整个撤掉、滚动全交宿主，结果详情页好了、**侧栏反而彻底滚不动**（详见 1.7.1）。顺带补上 `[data-run2skill-detection-route]` 的布局规则（此前一条都没有，这就是两个下拉挤在一行的原因）。
> 1.7.1 修正 1.7.0 的滚动结论。**同一个页面挂在两个位置，两条路径的父容器行为不一样**：插件详情页的 `.pageBody` 自己会滚，左侧栏的 `.mainPanel` 不会（它只有 `flex:1; min-height:0`，再往上 `.centreCol` 是 `overflow:hidden`，超出直接裁掉）。所以 1.7.0「滚动全交宿主」只对详情页成立，侧栏那条彻底滚不动。这次改为 `.page` 自己声明 `height:100% + overflow-y:auto`：侧栏父容器定高 → 生效、自己滚；详情页中间那层高度是 auto → `height:100%` 按 auto 处理、不产生溢出，仍由宿主滚，不会出现两条滚动条。同时补回细滚动条样式（部分主题把全局滚动条宽度设成 0，会「能滚但看不见」）。
> 1.8.0 修「语义检测 未完成」的两个真实根因。① **工具调得多 ≠ 观测残缺**：一整轮调了 500 多次工具时，旧逻辑把整条观测判成「不完整」，连带把已经提取好的用户原话丢弃成空数组；证据一空，模型无论答什么都绑不上，一律判成「模型输出非法」。现在工具摘要超上限只截断（保留最早 32 条），不再让整条观测作废。② **没什么可学的不该报成出错**：当一批里的用户消息全是截图、没有任何可引用的原话时，模型答什么都会失败，旧逻辑却把它记成「需要处理」要求用户看——用户根本无从下手。现在这类批次直接记为「这次没有可整理的内容」并跳过。
> 1.8.1 面板「看不全」的真正根因：**Grid 把每一行压扁了**。前两次（1.7.0 / 1.7.1）都在调页面自己的 `height` / `max-height` / `overflow`，方向全错——现场现象是页面根本不溢出（`scrollHeight === clientHeight`），所以没有滚动条。真正的成因是：`.page` 是 `display:grid` 且高度确定，而每个 `.section` 都带 `overflow:hidden`；按 CSS 规范，**子项 overflow 不是 visible 时，它的自动最小尺寸由 `min-content` 变成 `0`**，于是 grid 为了把 7 行塞进容器高度就把每行等比例压扁，区块再用自己的 `overflow:hidden` 把内容裁掉。这也解释了为什么手机、平板、桌面全都一样——跟容器多高无关。修法只有两行：`grid-auto-rows:max-content` + `align-content:start`。已用真实 Chrome 复现并验证：修前每块只剩 65px（正文需要 117px）、页面不可滚；修后每块 122–195px、页面可滚。
> 1.9.0 修「整条学习链路一条 Skill 都产不出来」的根因。此前你把功能做完一遍却什么都没生成——不是算法不灵，是**整个插件根本没启动过**。根因是三层的同一处：①插件用 `sha256` 把 DSH 自己的 standard preset 组合写死成白名单，DSH 一升级摘要就对不上，`captureRootConfiguration` 就抛 `V2_ROOT_CONFIGURATION_UNAVAILABLE`，该 Agent 永久不进作用域（本机日志里这条错误 4667 次，仍在每秒增长）；②这个失败被 catch 吞成一条笼统的 `AGENT_SCOPE_UNAVAILABLE`（8101 条），把真正的根因埋掉了；③解析 preset 自带 skills 目录时依赖 asar 内的模块布局，解析失败直接判死，而 `supportedConfiguration` 又要求「目录解析不到时 `customSkillDirs` 必须为空」，偏偏官方 preset 声明了 1 个——两头堵死。现在改为**摘要优先、结构兜底**：摘要对不上时按「preset 是 standard 且组合里仍有 `dsh-skill-filesystem`」认，再往下仍要过活 fiber 配置与 `supportedConfiguration` 两层校验，真正陌生的组合照样拒绝；失败原因也单独记一条同名健康码，不再混进笼统状态。

Run2Skill 把你在 DeepSeek Harness（DSH）里教给 Agent 的纠正、约束和工作流，整理成可复用的 Skill。你查看草稿、提出修改意见，确认后保存。

长会话通过有界 Pending Window 保留候选经验和相关反馈，后续判断可回读原始证据。默认保持标准召回；在 **插件 → Run2Skill → Skill 召回** 中可开启高级召回，配置 embedding 服务后使用 **BM25 + 向量 + RRF + 摘要重排**。重排默认沿用会话模型，也可配置专用服务。新建和合并前仍完整复核目录。模型、索引和失败回退说明见[高级召回](docs/features/hybrid-recall.md)。

## 安装

### 本机（DSH 0.2.3-alpha.2 桌面版）—— 推荐读这一节

本分叉**不走 npm**，用本地目录 + `link:` 挂载。装法如下（每一步都已在 2026-11-25 实测过）：

1. **准备插件目录**：下面用 `D:\dsh-plugins\dsh-run2skill` 作为示例路径，随便放哪都行，记住实际位置即可。

   > **从 GitHub 克隆的话，`lib\` 不存在**（仓库只收源码，构建产物在 `.gitignore` 里）。先构建一次：
   > ```bash
   > pnpm install
   > pnpm run build
   > ```
   > 成功后 `lib\` 会有 8 个文件：`client.js`、`index.js`、`index.d.ts`、`typert.host.js`、`typert.host.d.ts`、`typert.remote-client.js`、`typert.remote-client.d.ts`、`contract-*.js`。
   > 从本机备份目录 `version/20261125-v4/lib/` 直接拷一份也可以，字节完全一致。

   下面 2~6 步沿用这个示例路径；你装在别处就把路径整体替换成自己的。

2. **在 profile 里挂依赖**。编辑 `%USERPROFILE%\.dsh\profiles\desktop\package.json`，`dependencies` 加一行：
   ```json
   "@duma520/dsh-run2skill": "link:D:/dsh-plugins/dsh-run2skill"
   ```
3. **在 `dsh.profile.bundles` 数组里加一项** `"@duma520/dsh-run2skill"`（不加则宿主不会装配它的 Host/Client 半身）。
4. **建目录符号链接**（在 `%USERPROFILE%\.dsh\profiles\desktop\node_modules\@duma520\` 下）：
   ```cmd
   mklink /D dsh-run2skill D:\dsh-plugins\dsh-run2skill
   ```
   用 PowerShell 的 `New-Item -ItemType SymbolicLink` 也可以；若报没有权限，用 `python -c "import os; os.symlink(r'D:\dsh-plugins\dsh-run2skill','dsh-run2skill',target_is_directory=True)"`。
5. **改 `cordis.patch.yml`**：找到 `- id: run2skill` 那一行，把 `name` 改成 `"@duma520/dsh-run2skill"`（**必须带引号**，YAML 里以 `@` 开头的裸标量是非法的）。`config.automaticLearning` 保留原值。
6. **彻底退出并重启 DSH 桌面应用**。前端与 bundle 清单只在启动时装配一次，热刷新不生效。

重启后验证：左侧栏 **插件** 里出现 `dsh-run2skill` 卡片，版本 `1.9.0`，`未运行` 的红字不兼容提示消失。

### 为什么不能用 `dsh plugin` 命令行

`dsh plugin --profile desktop ...` 会直接报：

```
error: profile "desktop" is managed exclusively by the Electron application
```

desktop profile 由 DSH 桌面应用独占管理，CLI 完全无法装/改。要么走上面的手工配置，要么走 GUI 插件市场的「安装 bundle」。

### 上游原始安装说明（Web / Mac / 旧版 Windows）

以下为上游项目的通用装法，仅供其他宿主参考；`dsh-run2skill@1.0.0` 在 DSH 0.2.3-alpha.2 上会被门禁拦下。

**Web（DSH 0.2.2-rc.1）**：准备好 Node.js `>=24.9.0`、`pnpm` 和 `dsh` 命令，安装 `1.0.0`：

```bash
dsh plugin --profile web add dsh-run2skill@1.0.0
```

**Mac 桌面版（DSH 0.2.2-rc.3）**。首次打开 DSH 后，在应用菜单中选择 **管理 dsh 命令… → 安装**。完全退出应用，再在新终端运行。

```bash
dsh plugin --profile desktop add dsh-run2skill@1.0.0
```

**Windows Desktop（DSH 0.2.0-rc.2）**：通过 **Manage dsh Command…** 配置命令，完成首次启动后退出应用，安装 `0.5.0-alpha.4`：


安装后重启 DSH。Run2Skill 使用当前会话选择的模型。版本信息见 [兼容性](docs/compatibility.md)。

## 使用

照常与 Agent 工作，把值得复用的做法说清楚：

- **纠正**：“先写失败测试，再修实现。”
- **约束**：“这个项目的 GitHub 文案统一用中文。”
- **工作流**：“先核对上游版本，再运行兼容性检查。”
- **保存请求**：“把这个流程保存成 Skill，以后复用。”

Run2Skill 在会话空闲或收到保存请求时整理经验。有草稿需要审核时，DSH 会通知你。也可以打开插件页，点击**立即整理本次经验**。

每份草稿都附有对话来源。你可以确认保存、要求修改，或放弃草稿。Skill 支持保存到**当前项目**或**所有项目**，使用 DSH 默认的 Skill 目录。

## 设置

- **整理状态**：查看当前会话的经验整理进度。插件启用时自动生成草稿，也可手动请求立即整理。
- **最近活动**：查看最近 7 天新建或更新的 Skill。
- **语义检测用哪个模型**：给「没有记录用过哪个模型」的轮次指定检测模型。1.7.0 起是一张可排序的候选列表，见下一节。
- **清理所有缓存**：预览并清理待处理草稿与中间缓存，保留已保存的 Skill、会话记录和 DSH 设置。

Run2Skill 在本地管理草稿，并将经过筛选和脱敏的必要对话片段交给当前模型分析。详见 [数据存储与升级](docs/storage-and-upgrades.md)。

## 语义检测用哪个模型（1.7.0 起改成优先次序）

### 这一区解决什么问题

DSH 判断「这一轮对话到底用了哪个模型」，靠的是会话日志里的 `request/header` 事件。但**不是每一轮都会记它**——实测 20 轮的会话里有 11 轮窗口内完全没有这个事件。没有路由，检测器就没法证明模型答案绑定了哪个模型，这类轮次以前直接判死、永不重试。

这一区就是给那些轮次一个「明确告诉你用哪个模型」的出口。

### 位置

设置 → 插件 → `dsh-run2skill` → 展开 **语义检测用哪个模型**（默认折叠，点标题展开）。左侧栏「技能沉淀」面板里也有同一块。

### 怎么用（三步）

1. 点列表下方的 **新增一个候选**（1.7.0 之前是直接给两个空槽位）。
2. 第一列选 **provider**（DeepSeek API、DeepSeek Account、WorkBuddy、豆包……这一列是这台设备已经接通的），第二列选 **model**（会随 provider 变化，只列该 provider 的模型）。
3. 需要第二个、第三个备选就再点一次「新增一个候选」，然后用每行右侧的 **↑ / ↓ / 删除** 调整顺序。

检测时**从上往下逐个试，第一个能用的就赢**。排在最上面的相当于以前说的「主选」，第二行往后相当于「兜底」——但不再限制只有两个位置，最多 8 个。

### 几个要知道的点

- **保存是即时的**，没有「保存」按钮。每次改动立刻落盘，重开页面还在。
- **保存失败会说话**。失败时列表下方会出现 `未保存：<宿主给的原话>`，并且**你刚排的顺序不会被打回**——回滚会让人以为自己点错了。把这句话记下来就能定位问题。
- **某一轮本身带着可用模型信息时，仍然优先用那一轮的**，不会被这里排的列表覆盖。这里只对「没有可观测路由」的轮次生效。
- **一个候选都不加也可以**，此时行为与 1.5.0 完全一致。
- **走候选模型跑出来的批次会带 `fallback` 标记**，方便事后核对「这一条不是用会话原本的模型整理的」。
- **provider 换成另一个时，该行的 model 会被清空**，避免留下跨 provider 的无效组合。
- 一行里 provider 和 model 只填了一半时，**不会被存进去**（半截组合不是配置），但也不会阻止你继续填——填完另一半就会自动生效。

### 1.7.0 之前为什么「怎么选都是不指定」

1.6.0 到 1.6.2 用的是宿主的配置表单（configForms）通路。那条链路是 `configForms → settings.mutate → config-editor.edit → 回读 YAML 校验`，四层里任何一层失败，最终只给客户端回一个 `false`，**失败原因被整个丢掉**。界面上因此表现为：下拉能展开、能点，但选完值立刻弹回「不指定（跟随会话）」，后面的模型下拉永远灰着「先选 provider」。

1.7.0 起改走插件**自己的** RPC 端点（`detection-routes/get` / `detection-routes/set`）+ 自己的存储域，不再经过那四层。失败时 `Error.message` 原样带回客户端显示出来。

## 左侧栏入口（1.3.0 起）

插件启用后，左侧导航栏会多出一行 **技能沉淀**（在「回合通知」下面）。点它就直接切到本插件的整页面板，内容与插件详情页里的配置区完全一致，不用每次翻到插件页去找。

三个入口都在：

| 位置 | 长什么样 | 点了会怎样 |
| --- | --- | --- |
| 左侧导航栏 | 一行「技能沉淀」，带 ✨ 图标 | 切到本插件整页面板 |
| 插件详情页 | 一个「打开技能沉淀」按钮 | 同上 |
| 侧栏主面板 | 整页界面 | 整理状态、待处理、最近活动、技能使用情况、设置 |

如果左侧栏没出现这一行：宿主版本较老、不支持 `layout` 服务时会自动跳过侧栏注册（设置页与插件详情页照旧可用），此时改从 **插件 → dsh-run2skill → 配置** 进入即可。

## 「待处理」到底是什么（1.3.0 起文案已改，1.4.0 起自动跳过的不再逐条占位）

「需要处理」列表里的每一条，都是**一次没能自动整理完的经验**。它不是报错，也不影响已有 Skill 和会话记录。常见只有两种，看到时不用紧张：

| 界面标题 | 真实含义 | 你该做什么 |
| --- | --- | --- |
| 这次经验先不整理了 | 你在那段对话之后又继续说话了，系统担心拿旧内容做 Skill 会不准确，主动停下 | 不用管；想整理就在当前对话里重新说明一遍做法 |
| 需要你确认是否已经保存过 | 系统缺少这段对话开始前的 Skill 清单，不确定 Agent 是否已经存过同类 Skill | 点「不再处理这次经验」，或重新说明一遍做法 |

每条卡片下面还有两样东西：

- **一行进度摘要**（如「停在了『重复保存检查』这一步，后面的步骤没有开始。」）——告诉你停在哪，不再一次列五行「未开始」让你误以为五处都坏了。
- **本次处理的技术信息**（可折叠）——里面有五个步骤的完整分步状态和用到的模型，排查时看这里。

### 1.4.0 起：自动跳过的折叠成一条

上面第一种（「这次经验先不整理了」）**没有任何需要你决定的事**，逐条列成卡片再给一个按钮，等于假选择。1.4.0 起它们被折叠进一条汇总行：

> **3 次经验没有整理，这是正常的**
> 你在那段对话之后又继续说了话，系统担心拿旧内容做 Skill 不准确，就自动停下了。不需要你做任何决定，已有 Skill、会话记录和日志都没有受影响。
> 　　[ 知道了，收起这 3 条 ]

点一次就把这 3 条一起收掉，不会再占着「需要处理」。列表顶部那个计数只会算**真正需要你决定**的条数；如果全是自动跳过，会直接显示「没有需要你决定的事项」。

按钮含义（仍然逐条出现的，都是真正需要你决定的）：

- **不再处理这次经验**：只把这条从列表里移除。已有 Skill、会话记录、插件日志**都不会被删除**。
- **重试检索一次**（只有检索临时失败时才出现）：让插件重新跑一次已有 Skill 检索。
- **使用已有 Skill，不生成草稿**（只有判定可能重复时才出现）：承认已有 Skill 已覆盖，不再生成新草稿。

## 「高级召回」到底要不要开（1.4.0 起写清楚了）

代码路径：`插件 → Run2Skill → Skill 召回 → 高级召回`。**默认关闭，而且大多数情况就该保持关闭。**

它决定的是「去找已有 Skill」时怎么缩小范围：

| | 关闭（默认，推荐） | 打开 |
| --- | --- | --- |
| 怎么找 | 逐页读每个 Skill 的摘要做匹配 | 先算语义向量筛出相关技能，再逐条核对正文覆盖 |
| 要什么外部服务 | **不需要**，全部在本机算 | **需要你自己的 Embedding 服务**（填接口地址、模型名、凭证的环境变量名） |
| 费用 | 零额外费用 | 每次检索都会调用你的向量服务，按你自己的服务计费 |
| 适合谁 | Skill 在几十个以内 | Skill 已经几百个、逐页翻明显变慢 |
| 连不上会怎样 | —— | 自动退回标准召回，不会报错、不会中断整理 |

判断标准很简单：**你没有自己搭过 embedding 服务，就别勾。** 勾了也只是让它每次先去连一个填错的地址，然后退回标准召回，白白多一次失败等待。

如果确实要开：接口地址与模型名照服务商的文档填（模型默认 `Qwen/Qwen3-Embedding-0.6B`），凭证那里**只写运行 DSH 那台机器上的环境变量名，密钥本身不要填进来**。填好后回「需要处理」点一次刷新试一下，连得上就正常工作，连不上会自动退回，不会留下坏状态。

## 1.2.0 新增的四项能力

这四项都是「出错时能查、改坏时能退、不是同一版时能看出来」，不改变上游的业务流程。

### 1. 插件自有落盘日志

- 路径：`~/.dsh/dsh-run2skill/logs/run2skill.log`（Windows 是 `%USERPROFILE%\.dsh\dsh-run2skill\logs\run2skill.log`）。
- 格式：每行一个 JSON 对象，含 `ts` / `level` / `name` / `message` / `args`。文件权限 `0600`。
- 轮转：单个文件超过 **5 MB** 时改名为 `run2skill.log.1`（只保留一份旧档，不做无限堆积）。
- 脱敏：写入前逐字段脱敏，密码类键值赋值、认证请求头、bearer 令牌、URL 内嵌凭据等一律替换为 `[REDACTED]`；结构化字段（数字、布尔、数组）原样保留。
- 安全阀：**任何写日志失败都不会抛出**，只静默降级——日志不能打断 Agent 主循环。
- 记录内容：插件装载/就绪/卸载、ingress 健康码、代际过期告警、代际探测失败。排查问题时先看这里。

### 2. 运行代际自检（需重启时会明确告诉你）

插件在模块导入时对**正在运行的这份代码**算一次 SHA-1 指纹（12 位），之后每次读取设置页都会重读磁盘上的同一文件比对：

- 两侧一致：设置页不显示任何提示。
- 磁盘已换新版（例如你更新了插件但没重启）：设置页顶部出现红色横幅，写明「运行中的插件是旧版本（运行 xxx），磁盘上已是新版本（磁盘 yyy）。请重启 DSH 桌面应用后生效。」
- 任一侧指纹读不出来：**不报警**（宁可漏报也不误报）。

> 为什么需要这个：DSH 的插件界面改动不随热刷新生效，以前只能靠「改了没反应」来猜。现在它会直接告诉你磁盘和内存不是同一版。探测节流为 60 秒一次，不会每次轮询都读盘。

### 3. 技能使用情况（召回遥测）

设置页新增「技能使用情况」折叠区，显示**最近 30 天**每个 Skill 被读出来交给模型的次数：

- 数据来源：直接读 v2 域里 `experience_intents` 的召回候选，**不额外落一份派生索引**——同一件事不存两遍，也不会与主数据不一致。
- 计次口径：只有 `bodyDigest` 存在（正文真被读出来）的候选才算一次；同一次召回里重试不会重复计数。
- 作用域：`仅当前项目可用` / `所有项目可用` / `来源未知`。项目级记录必须能确定归属到某个工作区才算数，归不了属的一律丢弃，**不把多个工作区的数字合并成一个误导性总数**。
- 诚实边界（界面上也写着）：**只表示这些 Skill 的正文被读出来交给了模型，不代表模型真的用上了它们。**
- 与会「最近活动」的区别：「最近活动」是**写侧**（新建/更新了哪些 Skill），「技能使用情况」是**读侧**（哪些 Skill 被拿出了）。两者分开，不混成一个数字。

### 4. 发布历史快照（改坏了能找回上一版）

- 每次**合并更新**一个已存在的 Skill 时，被替换掉的旧正文会先归档到 `skills/.run2skill-history/<skill-name>/<内容哈希>.md`（与 `SKILL.md` 同级目录下的隐藏目录）。
- 每个 Skill **最多保留 3 个历史版本**，超出按修改时间删最旧。
- 按内容哈希命名，所以崩溃重试只会把同样的字节拷到同样的名字，天然幂等。
- 首次创建不产生历史（没有旧版本可留）。
- 归档失败**不会回滚**一次已经校验通过的发布——历史副本是尽力而为，不能因为它写不进去就把刚发布的好版本撤掉。
- 恢复方法：把 `history/<哈希>.md` 手工拷回 `SKILL.md` 即可（插件不提供自动回滚按钮，避免误操作覆盖你要保留的版本）。

## 更新与卸载

按上方安装说明选择与宿主匹配的版本，安装后重启 DSH。

**本机分叉版的卸载 / 回滚**（手工操作，因为 desktop profile 不能用 CLI）：

1. 从 `%USERPROFILE%\.dsh\profiles\desktop\package.json` 的 `dependencies` 删掉 `"@duma520/dsh-run2skill"`，从 `dsh.profile.bundles` 删掉 `"@duma520/dsh-run2skill"`。
2. 从 `cordis.patch.yml` 删掉整段 `- id: run2skill` 行（或把它注释掉）。
3. 删掉 `%USERPROFILE%\.dsh\profiles\desktop\node_modules\@duma520\dsh-run2skill` 这个符号链接。
4. 重启 DSH 桌面应用。

**回滚到上游原插件**：把 `node_modules\dsh-run2skill.disabled-by-duma520` 改回 `node_modules\dsh-run2skill`，并把 `package.json` 里 `"dsh-run2skill": "1.0.0"`、`bundles` 里的 `"dsh-run2skill"`、`cordis.patch.yml` 里 `name: "dsh-run2skill"` 一并恢复。本次改动前的原始文件已备份在 `%USERPROFILE%\.dsh\profiles\desktop\.backup-run2skill\`。

上游通用卸载命令（其他宿主适用）：

```bash
dsh plugin --profile desktop remove dsh-run2skill
```

Web 用户将 `desktop` 换成 `web`。卸载后已保存的 Skill 和插件数据继续保留；需要清理缓存时，可在卸载前使用插件页的清理功能。

| 1.5.0 | 2026-11-27 | 修「从来学不会任何 Skill」的三个根因：模型回复带 reasoning/tool-call 块时整条观察被判不完整（实测 245/265 轮次死于此，证据被一并清空导致检测永远失败）；路由继承的回填分支因标志位过早置位而永不触发（无 request/header 的轮次整批判 ROUTE_UNAVAILABLE）；带图片的轮次改为只取文字块做证据（纯图片仍失败关闭）。另新增「一键全部不再处理」，一次清掉只有单一选项的条目，带重试的条目不受影响 |
| 1.6.0 | 2026-11-27 | 设置页新增「语义检测用哪个模型」：可从本机已接通的 provider 现读模型清单并指定检测模型与兜底模型，解决「这一轮没记录用过哪个模型」的轮次以前直接判死、永不重试的问题；只填一半不算配置，观测到的路由仍优先，兜底批次带 fallback 标记 |
| 1.6.1 | 2026-11-27 | 新建会话还没选工作区、或会话目录不在任何已登记项目里这类**正常**情形，以前被统一说成「读不到整理状态、归属对不上」，看着像插件坏了；现在单列为 `UNSCOPED` 并直接说明会话不在当前项目里。真出错的文案也不再拿「归属对不上」当默认解释；反方向——会话确实绑定了项目却被按「仅用户」层级去问——仍然照样拒绝 |
| 1.6.2 | 2026-11-27 | 修两个接线错误：`model-catalog/list` 与 `recall-telemetry/list` 忘了登记进端点白名单，导致模型清单永远读不到、设置页只能手动填 id；侧栏容器无定高使 `height:100%` 退化为 `auto`，面板一直滚不动，现补 `max-height` 与显式滚动条样式。模型一栏在能读到清单时一律为下拉框 |
| 1.7.0 | 2026-11-28 | 「语义检测用哪个模型」改成**用户自定义优先次序**：不再只有「主选 + 兜底」两个位置，而是一张可上移/下移/删除的有序候选列表（最多 8 个），检测时从上往下逐个试，第一个能用的就赢。同时真正修好面板滚动——此前插件自己在 `.page` 上又套了一层 `max-height:calc(100vh-88px)` 的自滚容器，把宿主已提供的滚动容器顶掉了，内容被外层裁掉又不触发滚动；滚动这部分在 1.7.1 里被推翻重做 |
| 1.7.1 | 2026-11-28 | 修正 1.7.0 的滚动结论：**同一个页面挂在两个位置，两条路径的父容器行为不一样**。插件详情页的 `.pageBody` 自己会滚，左侧栏的 `.mainPanel` 不会（它只有 `flex:1; min-height:0`，再往上 `.centreCol` 是 `overflow:hidden`，超出直接裁掉）。所以 1.7.0「滚动全交宿主」只对详情页成立，侧栏那条彻底滚不动。这次改为 `.page` 自己声明 `height:100% + overflow-y:auto`：侧栏父容器定高 → 生效、自己滚；详情页中间那层高度是 auto → `height:100%` 按 auto 处理、不产生溢出，仍由宿主滚，不会出现两条滚动条。同时补回细滚动条样式（部分主题把全局滚动条宽度设成 0，会「能滚但看不见」） |
| 1.8.0 | 2026-11-28 | 修「语义检测 未完成」的两个真实根因。①**工具调得多 ≠ 观测残缺**：一整轮调了 500 多次工具时，旧逻辑把整条观测判成「不完整」，连带把已经提取好的用户原话丢弃成空数组，于是模型无论答什么都绑不上证据、一律判成「模型输出非法」。现在工具摘要超上限只截断（保留最早 32 条），不再让整条观测作废。②**没什么可学的不该报成出错**：当一批里的用户消息全是截图、没有任何可引用的原话时，模型答什么都会失败，旧逻辑把它记成「需要处理」要求用户看——但用户根本无从下手。现在这种批次直接记为「这次没有可整理的内容」并跳过，不再弹「需要处理」 |
| 1.8.1 | 2026-11-28 | 面板「看不全」的真正根因：**Grid 把每一行压扁了**。`.page` 是 `display:grid` 且高度确定，每个 `.section` 又带 `overflow:hidden`——按 CSS 规范，子项 overflow 不是 `visible` 时自动最小尺寸由 `min-content` 变成 `0`，于是 grid 把 7 行等比例压扁以塞进容器，每个区块再用自己的 `overflow:hidden` 裁掉内容。前两次（1.7.0 / 1.7.1）调 `height` / `max-height` 方向都错了，因为页面根本不溢出。修法两行：`grid-auto-rows:max-content` + `align-content:start` |
| 1.9.0 | 2026-11-29 | 修「整条学习链路一条 Skill 都产不出来」的根因。此前功能从未真正跑通一次（`proposal_lineages` 恒为 0）：插件用 `sha256` 把 DSH 自己的 standard preset 组合写死成白名单，DSH 升级到 0.2.3-alpha.2 后摘要对不上，`captureRootConfiguration` 抛 `V2_ROOT_CONFIGURATION_UNAVAILABLE`，该 Agent 永久不进作用域（本机日志 4667 次）；该失败又被 catch 吞成一条笼统的 `AGENT_SCOPE_UNAVAILABLE`（8101 条），把根因埋掉。另有第三处：解析 preset 自带 skills 目录依赖 asar 内模块布局，解析失败直接判死，而 `supportedConfiguration` 要求「解析不到时 `customSkillDirs` 必须为空」，官方 preset 却声明了 1 个。改为摘要优先、结构兜底（preset 是 `standard` 且组合里仍有 `dsh-skill-filesystem`），下游活 fiber 配置与 `supportedConfiguration` 两层校验仍全部保留 |
